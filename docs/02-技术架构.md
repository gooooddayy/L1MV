# 02 · 技术架构

## 1. 单文件里装了什么

```
播放器视频生成器.html
├─ <head>    meta / OG / JSON-LD（SEO 用，不参与运行）
├─ <style>   22 KB，全部样式内联（无外部样式表、无 @import、无外链字体）
├─ <body>    界面 DOM（顶栏 / 舞台 / 参数面板 / 歌词表 / 移动端页签）
├─ <script>  217 KB，一个 IIFE 风格的主脚本，无模块、无打包器、无 polyfill
└─ #fontStore
     5 段 <script type="text/plain">，共 6.5 MB base64
     浏览器只当纯文本扫过（找 </script>），不解析、不执行
```

### 为什么字体不进 CSS

`<style>` 里放 6.4 MB base64 时，CSS 解析器要对每个 token 做词法分析 + 字符串驻留，HTML 解析从 40 ms 涨到 **590 ms**，FCP 2.6 s。挪进 `text/plain` 后解析降到 **32–51 ms**。

这是整个项目收益最大的一处改动，也是最反直觉的一处：**同样大小的数据，放在不同标签里，代价差 15 倍。**

## 2. 全局状态与「场景隔离」

渲染器不是纯函数式的——它依赖一批模块级全局（`L / W / H / RS / assets / layout / state / ctx / cv / overlays`）。要在「界面预览 1080」和「导出 2K」之间来回切而不互相污染，用了三件套：

```js
grabGlobals()        // 打包当前全局
setGlobals(g)        // 换一套全局
withScene(scene, fn) // 换 → 画 → 还原（try/finally，中间没有 await）
```

导出时：

```js
const scene = buildScene(K);   // 按目标分辨率重建布局、静态层、离屏画布、state 快照
// …逐帧 withScene(scene, () => renderAt(t)) …
disposeScene(scene);           // 画布置 1×1、释放布局；K≠1 时清字形缓存
```

几个刻意的选择：

- **离屏画布不入 DOM**：DOM 里的画布每帧要经合成器上传/读回，实测单帧 200 ms；离屏画布直接 `drawImage` 到 `VideoFrame` 快一个数量级。
- **`buildScene` 里 `state = snapshotState()`**：导出参数在点按钮那一刻钉死，之后用户改字号/颜色/歌词只影响预览。
- **`K === 1` 时布局原样复用**：保证 1080P 输出与旧版逐像素一致，不给「优化」留退路。
- **2K 导出后 `clearTextCache()`**：2K 的字形位图非常大，留着就是白占内存。

## 3. 渲染管线

```
buildAll()            重建静态素材（背景、封面卡、唱片、暗角、颗粒底）
   └─ buildBg()       整屏不透明底色（第一笔就是全屏填充）
buildLayout()         按字号/歌名长度算出每行歌词的位置与透明度曲线
renderAt(t)           每帧：静态层 drawImage → 封面/唱片旋转 → 歌词 → 叠加素材 → 特效
   ├─ drawCover()     封面（圆角、投影、可选弹出）
   ├─ drawLyrics(t)   逐行绘制，带位图缓存
   └─ drawOverlays(t) 图片/视频叠加（混合模式 + 透明度）
```

### 文字位图缓存

`shadowBlur` 每帧做一次真高斯模糊是最贵的一项。做法是把标题与歌词行**预渲染成位图**（带模糊与描边），每帧只 `drawImage`。

三个约束：
- 缓存键必须包含**字号、字体、颜色、DPR/RS**——少一个就会串味。
- 换字体后必须 `clearTextCache()` 再 `buildLayout()`，否则出现「切了字体还是旧字形」。
- 2K 下位图体积 ×4，导完必须清。

### 首帧时机

`requestAnimationFrame` 的回调在**绘制之前**执行：想「先让浏览器画出首屏，再干重活」，单级 rAF 等于没推。用两级 rAF + `renderAt` 里的 `if(!assets.bg) return` 兜住，FCP 从 1544 ms 降到 1148–1208 ms。

## 4. 分辨率缩放（K）

```js
K = 目标高 / 1080          // 720P→0.667，1080P→1，2K→1.333
L = scaleLayout(base, K)   // 布局按 K 重建，不是整体缩放位图
W = round(base.w * K); H = round(base.h * K)
RS = K                     // 渲染缩放，供文字缓存与线宽使用
```

**为什么重建而不是缩放位图**：整体缩放会让 1px 描边变糊、字距失真；按 K 重建布局 + 按 K 生成字形位图，2K 才是真 2K。

竖版同理：`LAYOUTS.portrait` 是 1080×1920 的一套独立参数（歌名在封面上方、整体居中、字号另算），不是横版旋转。

## 5. 移动端外壳

原则：**只加外壳，不动渲染与导出**。所有手机分支都被 `isPhone()`（`matchMedia('(max-width:700px)')`）挡住，PC 端一个分支都不进。

| 部件 | 做法 |
|---|---|
| 两页签 | 预览 / 样式，`transform: translateX` 跟手翻页（pointer 事件 + 阻尼），不是淡入淡出 |
| 自绘下拉 | `buildNiceSelect()` 接管原生 `<select>`：把菜单挂到 `body`（避开 `.pager` 的 transform/overflow 裁切），`position:fixed` + 先量 `offsetHeight` 再决定向上/向下翻 |
| 短标签 | 320px 下「快速编码」会被截成「快速编」，手机端换两字标签 |
| 自动降档 | 按 `deviceMemory` / 堆上限决定默认 720P 还是 1080P，并说明原因 |
| 常亮 | 录制期间 `navigator.wakeLock`，结束释放 |

自绘下拉的四个坑（互斥、点内部就关、残留已删选项、不触发 change）都在 [04-踩坑全集](04-踩坑全集.md) 里。

## 6. 能力探测与降级

```js
CAP = {
  encoder, audioEnc, decoder, audioDec,   // WebCodecs 四件套
  recorder, capture,                      // MediaRecorder + captureStream
  recMp4, recWebm,                        // 录制容器支持
  inert                                   // 老内核没有 inert
}
```

`applyCapabilities()` 在启动时把不可用的导出方式置灰、自动切到可用方式、状态栏写一句人话；两者都没有就禁用导出按钮。

**必须幂等**：能用的项要能恢复，且不能覆盖手机端的短标签——第一版只 disable 不 restore，测试里立刻暴露。

## 7. 任务与竞态

| 机制 | 防的是什么 |
|---|---|
| `beginJob()/jobOK()` 任务号 | 上一轮录制的重封装晚到时，改新任务的状态或触发多余下载 |
| `loadImageFile/loadAudioFile` 导入序号 | 连续选两段素材，先发的解码后回来，覆盖后选的 |
| `IntersectionObserver` | 预览离屏（手机翻到「样式」页）还在空跑 rAF |
| 堆 > 700 MB 自愈 | 切回页面时清字形缓存 + 释放大音频 PCM |

作废任务的回调**既不下载、也不改状态、也不碰 busy**——否则会出现「文件下好了、状态是上一次的」，或者把新任务的 busy 关掉。

## 8. 内存模型

```js
memBreakdown(ew, eh) =
    音频 PCM 全额          // 48k × 2ch × float32 ≈ 0.366 MB/s
  + 视频分片 × 50%         // 早期按 15% 估，对内存分片太乐观
  + 素材画布 55MB × 面积比
```

`suggestMaxSeconds(ew, eh, limitMB)` 用同一口径反推「这条片子最多能导多久」，超限文案直接列三项与总额，用户能看出该改哪个数。

实测：1080P 10 分钟 = 341 MB（旧模型只估 90 MB）；40 分钟 = 1190 MB；40 分钟 720P = 634 MB。

## 9. 日志

200 条环形缓冲（时间 / 级别 / 标签 / 内容），`logDump()` 一键导文本。**默认零 console 输出**——导出时打日志是纯 I/O 负担。`?debug=1` 才同时打 console，并挂 `window.__app`。

记录：启动能力、素材载入、录制起止、导出成功/失败/取消、内存自愈。
