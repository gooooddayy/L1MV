# 05 · 性能复盘

> 所有数字都是本机实测（Edge 156 / Windows / `file://`），不是估的。
> **没测过的一律标「未实测」**——看到这两个字别当结论用。

## 1. 测量环境与方法

| 项 | 值 |
|---|---|
| 浏览器 | Edge 156（Chromium），`file://` 直开 |
| 设备 | Windows 台式，核显 Intel HD 630 |
| 工具 | 自写 CDP 驱动（`.workbuddy/bench/`），`Performance` + `Profiler` 采样 |
| 启动参数 | `--disable-features=CalculateNativeWinOcclusion`、`--disable-backgrounding-occluded-windows`、`--disable-renderer-backgrounding` |

### 为什么要交替采样

机器负载会漂移。做法是**新旧版本交替跑**（A/B/A/B），每轮取中位数，而不是「先测旧的、再测新的」。否则一次后台更新就能让结论反转。

### 为什么窗口要放屏幕外还要关遮挡计算

Chromium 会把「窗口被遮挡」当成「用户看不见」，进而节流合成器与 GPU。实测同一段代码耗时在 17 / 29 / 49 ms 之间跳。`--disable-features=CalculateNativeWinOcclusion` 之后才稳定。

## 2. 首屏

| 指标 | 优化前 | v58 | v60（当前） |
|---|---|---|---|
| HTML 解析（responseEnd → domInteractive） | 586–619 ms | 32–51 ms | **19–47 ms** |
| 启动 JS（interactive → FCP） | 560–590 ms | 207–337 ms | — |
| FCP | 2588–2724 ms | 1828–2224 ms | **1148–1208 ms** |
| `<style>` 体积 | 6.40 MB / 171 条规则 | 0.02 MB / 166 条 | 21 KB |
| 启动到可交互 | 560–590 ms | ~0（首帧先画） | ~0 |

### 三个动作，按收益排序

1. **字体 base64 从 `<style>` 挪到 `<script type="text/plain">`**
   这一项单独贡献了 550 ms 的解析时间。原因：CSS 解析器要对每个 base64 URL token 做词法分析 + 字符串驻留；HTML 解析器只做一次纯文本扫描（找 `</script>`）。

2. **首帧渲染延到第一帧之后**
   两级 `requestAnimationFrame`（单级无效，回调在绘制之前）。FCP 再降 348 ms。

3. **字体探测挪到 `requestIdleCallback`**
   每个系统字族 3 次 canvas 测量，实测 133 ms。现在先只列内置 5 款 + 通用族。

### 没有做的

- 不做骨架屏：本身是白底工具，骨架屏反而多一次布局。
- 不做代码分割：单文件是产品约束。
- 不 minify：字体占 96%，去注释 + 压空白只能省 0.87%，却毁掉可维护性。

## 3. 交互

同一组用例 A/B：

| 用例 | 前 | 后 | 倍数 |
|---|---|---|---|
| 连发 60 次字号滑块 `input`（同步阻塞） | 1506.5 ms | **0.7 ms** | 2152× |
| 连打 20 个歌词字符 | 10.1 ms | **5.4 ms** | 1.9× |
| 200 次页签切换 | 9.7 ms（无异常） | 9.7 ms | — |
| 60 次拖进度条 | 48 ms | 48 ms | — |
| 30 次清空/粘贴 | 9.2 ms | 9.2 ms | — |
| 50 次播放/暂停 | 13.6 ms | 13.6 ms | — |

### 关键改动

- `refreshPreview(rebuild)`：滑块/颜色/歌词输入全部合并到下一帧，一帧只 `buildLayout + renderAt` 一次。**只有预览刷新走这条路**，seek 与导出仍同步（否则会看到旧帧）。
- 切页签的重绘移到 rAF，滑动动画先起步（体感优先）。
- 去掉 header / 底栏的 `backdrop-filter: blur(14px)`：sticky 元素每帧对整宽做高斯模糊。
- 下拉监听从「每个下拉 3 个文档级监听」收敛成一套。

## 4. 导出

| 场景 | 耗时 | 备注 |
|---|---|---|
| 1080P 10 秒（特效全开） | **5.1 s** | 约 2× 速 |
| 1080P 20 秒 | **10.7 s** | 优化前 10.9 s |
| 720P 2 秒 | 1.8 s | — |
| 编码器吞吐上限 | 86 fps | Intel HD 630 |
| 每帧 | 17 ms | 渲染 8 + 编码 11.6，同一颗 GPU 串行 |

### 为什么只优化下来 0.2 秒

因为瓶颈在硬件编码器，不在渲染。20 秒 × 30 fps = 600 帧，600 / 86 fps ≈ 7 s 是编码本身的物理下限，加上渲染与封装，10.7 s 已经贴着上限。

唯一落地的改动：`renderAt` 有 `assets.bg` 时不再先铺底色（buildBg 第一笔就是整屏不透明填充），每帧省一次 1920×1080 全屏 `fill`。

### 实测否决的方向（别再试）

| 方向 | 实测 | 结论 |
|---|---|---|
| 双画布交替 | 无差异 | 否 |
| 队列深度 4 / 8 / 12 | 噪声内 | 否（深度只影响显存安全） |
| `alpha: false` | 无差异 | 否（已默认不透明） |
| 强制软件编码 | 更慢 | 否 |
| `latencyMode: 'realtime'` | 3.28 vs 3.32 s | 否，且降画质 |
| `bitrateMode: 'constant'` | 无提速 | 否 |
| 双 VideoEncoder 并行 | 2.51/2.48 vs 2.61/2.44 s | 否，核显只有一个编码引擎 |
| 让出策略 all / 2 帧 / time(12ms) / 不让 | 5.28/5.30/5.29/5.33 s | 全等 |

> 教训：**编码路径上的优化必须先测量**。六个「看起来该有效」的方向，收益全是 0。

## 5. 内存

| 场景 | 结果 |
|---|---|
| 空闲 3 秒主线程 TaskDuration | **0 ms** |
| 导出后 JS 堆 | 3.7 MB → GC 后 1.1 MB |
| 长稳 10 轮导出（穿插切页签 + 改字号） | 堆恒定 **9.5 MB**，无衰减 |
| 1080P 10 分钟预算 | 341 MB（旧模型只估 90 MB） |
| 40 分钟 1080P / 720P | 1190 MB / 634 MB |

### 模型

```
memBreakdown = PCM 全额 + 成片大小 × 50% + 素材画布（55MB × 面积比）
```

早期视频分片按 15% 估，对内存分片太乐观；改成 50% 后，超限提示能直接告出「该改哪个数」。

### 护栏

- 运行中：每 32 帧查 `performance.memory`，超 1200 MB（手机）/ 2600 MB（PC）主动停。
- 导入时：`probeAudioSeconds` 预估 PCM > 1800 MB（≈80 分钟）直接拒收。
- 交付后：PCM > 300 MB 的音频缓存主动释放（1 小时立体声常驻 1.3 GB）。
- 切回页面：堆 > 700 MB 清字形缓存 + 释放大音频。

## 6. 低端与断网

CPU 降速 4× + 离线：

| 用例 | 正常 | 降速 + 断网 |
|---|---|---|
| 60 次滑块同步 | 0.7 ms | 2.9 ms |
| 50 次切页签 | 1.3 ms | 8.9 ms |
| 单帧渲染 | 3.7 ms | 19.2 ms |
| 2 s 720P 导出 | 1809 ms | 1972 ms（+9%） |

结论：断网零影响（本来就没有请求）；降速主要影响渲染，导出只慢 9%（编码器不受 CPU 降速影响）。

## 7. 边界

| 场景 | 结果 |
|---|---|
| 1000 行歌词 | 导入 36 ms、滚动 61 fps、5238 个 DOM 节点 |
| 1440@2x / 1024@3x | 无横向溢出 |
| 浏览器缩放 125% / 150% | 无溢出 |
| CLS | **0** |
| 200 次页签切换 | 无异常、状态一致 |

> 1000 行歌词没做虚拟滚动：36 ms 导入 + 61 fps 滚动已经够，改动风险大于收益。
