# 04 · 踩坑全集

> 49 条，全部是实际撞过的。每条写「症状 → 根因 → 修法」，少数补了「判据」（怎么确认真的修好了）。
> 顺序按类别，不按时间。**动手改之前先扫一遍，能省一天。**

## A. 编码与封装（13 条）

### A1. 碎片 MP4 不能直接播
**症状**：导出的 MP4 在微信/相册里打不开，或显示时长 0。
**根因**：MediaRecorder 写的是「边录边写」的碎片结构（moov 在前 + 多个 moof），不是规整 MP4。
**修法**：解析 `stbl` 重封装成规整 MP4（`remuxRecordedMP4`）。

### A2. 压长帧会把时间轴压短
**症状**：低配机上 3.46 秒的片子变成 1.84 秒，整条加速。
**根因**：早期为消除「暂停造成的超长帧」，把大时长压成中位数。
**修法**：移除该逻辑。超长帧是真实时间，不能压。

### A3. 裁剪必须落在关键帧
**症状**：前 3 秒只有声音、画面黑，进度条拖不回去。
**根因**：MediaRecorder 的 IDR 间隔可达几秒，裁过头把开头唯一的解码起点切掉了。
**修法**：要么不裁开头（当前选择），要么在关键帧处裁。

### A4. 全片只有 1 个 IDR
**症状**：拖动进度条要等很久，甚至卡死。
**根因**：MediaRecorder 实时录制只在开头写一个关键帧。
**修法**：不重编码无解。已列为已知限制；快速编码路径是 2 秒一个 IDR。

### A5. VFR 不能按固定帧长写
**症状**：4:06 的片子画面 2:50 就播完，声音还在走（比例 0.686）。
**根因**：转换时一律按 1/30 秒写 `stts`，而录制是 VFR（手机 ~20 fps）。
**修法**：按相邻时间戳算每帧时长 `d = round(Δt × 0.09)`（µs → 90 kHz），最后一帧 +33 ms。
**判据**：20 fps / 7.9 s 的 WebM，修前视频轨 5.07 s，修后 7.93 s，音频 7.94 s。

### A6. WebM 的 Cluster 是「未知长度」
**症状**：6 秒录制只转出 3.35 秒，后面全丢。
**根因**：Cluster 长度写成 `0x01FFFFFFFFFFFFFF`（未知），解析器当成「一直到文件末尾」，遇到第二个 Cluster 就 break。
**修法**：外层 `end` 改 `let` 且允许回缩；遇到 `0x1F43B675`（下一个 Cluster 头）或未知长度子元素就 `end = cp` 提前收尾，`pos = end` 继续下一个。

### A7. WebM 没有 Duration
**症状**：播放器显示 0，放不了，拖不动。
**根因**：MediaRecorder 边录边写，Info 里没有 Duration，读出来是 `Infinity`。
**修法**：`fixWebm()` 重写 Info（TimecodeScale + Duration + 应用名）与每 1 秒一簇的 Cluster。
**判据**：6 s 录制修前 Infinity，修后 6.02 s、可拖到 3.0 s。

### A8. VP9 是全范围
**症状**：转换后的画面整体偏暗（`#112233` → `#011628`）。
**根因**：`VideoDecoder` 默认按有限范围（limited range）报色彩。
**修法**：`configure` 里显式 `colorSpace: { fullRange: true }`。
**判据**：源 (16,35,51) / 成片 (16,35,52)。

### A9. Chrome 把视频帧写成 BlockGroup
**症状**：解析时报「WebM 开头没有关键帧」。
**根因**：Chrome 用 BlockGroup 包 Block，且不填 Block 的关键帧标志位。
**修法**：按 Matroska 规范「**没有 ReferenceBlock 就是关键帧**」判断。

### A10. 宽高/采样率藏在子元素里
**症状**：`Invalid coded size (0,0)`。
**根因**：宽高在 `Video(0xE0)`、采样率/声道在 `Audio(0xE1)` 里，第一层 TrackEntry 上是空的。
**修法**：下钻一层读。

### A11. AAC 有 priming
**症状**：音频比画面晚 60–80 ms，短片上特别明显。
**根因**：Chrome 编码时额外加 2–3×1024 个样本，容器时长虚高。
**修法**：音频轨写 `elst`（edit list）校正起点。

### A12. 没有 avcC 封不出 MP4
**症状**：`编码器没有给出 avcC，无法封装 MP4`。
**根因**：`avcC` 在第一个 chunk 的 `decoderConfig.description` 里，只出现一次；漏接就没了。
**修法**：`output` 回调里第一次见到就存下来，封装前断言存在。

### A13. 编码错误会在 flush 之后才出现
**症状**：导出显示成功，文件却打不开。
**根因**：`VideoEncoder` 的 `error` 回调可能晚于 `flush()`，而 `close()` 会把异常吞掉。
**修法**：`flush` 后再查一次 `encErr`；出片后校验帧数与时长。

## B. 音频（7 条）

### B1. `<audio>.duration` 读的是文件头
**症状**：4:06 的音频导成 4:08，尾部多 2 秒静音。
**根因**：VBR MP3 的文件头时长常差 1–2 秒，时长基准跟着错。
**修法**：导入即 `decodeAudioData`，以 `audioBuf.duration` 为准；差 >0.15 s 才改并提示。

### B2. AAC 编码器会挑码率
**症状**：某些安卓机 192k 报错，128k 却能编。
**修法**：`[192000, 128000, 96000]` 逐档重试。

### B3. `isConfigSupported` 会撒谎
**症状**：查询说没有 AAC，实际能编；据此降级导致整条片子变 WebM。
**根因**：部分内核的查询实现不完整。
**修法**：改成**真编 4096 帧**判断（`aacWorks`）。1024 帧会让 `flush` 报「Flushing error」，那是探测方法的问题。

### B4. 把 `audioCodec` 写成 `'pcm'`
**症状**：`Unsupported channel count … received 0`，每次都退 PCM。
**根因**：自己挖的坑——返回对象里写了 `audioCodec: audioPCM ? 'pcm' : audioCodec`，然后 `AudioEncoder.configure({codec:'pcm'})` 必炸。
**修法**：`audioCodec` 永远是真实编码器名（`mp4a.40.2`）；`audioPCM` 只作提示。

### B5. PCM 塞进 MP4 是「少见组合」
**症状**：mp4 + sowt 在 Chrome 能播，但 `decodeAudioData` 直接报错（解不出音频）。
**修法**：PCM 只进 MOV。能编 AAC 就老实 MP4；编不了才 MOV，并在状态栏写明原因。

### B6. 音轨起点没对齐
**症状**：音画差几十毫秒，短片上能听出来。
**根因**：转换时音频从 0 连续写，抹掉了 WebM 里音/视频第一条块的时间戳差。
**修法**：以画面第一帧为 0；晚 `headPad` 补静音，早 `-headPad` 裁掉；中途丢包（跳变 >3 ms）也补静音。

### B7. HE-AAC 每包 2048 样本
**症状**：用 HE-AAC 时音频变半速。
**根因**：写死 1024 样本/包。
**修法**：按时间戳算每包样本数；`MP4.build` 里 `aPer`（音频自带时长）时跳过按 1024 的尾部截断。

## C. 字体与排版（5 条）

### C1. CSS 注释少写 `*/`
**症状**：字体全部失效，但页面还能开。
**根因**：注入 6.6 MB 字体样式时注释没闭合，把后面整段 CSS 吞了。
**修法**：大段 CSS 注入后校验 `*/` 配对；用 `document.fonts.check` 抽查。

### C2. 字体是按需加载的
**症状**：切了字体，当帧还是旧字形；导出的片子里字体也没生效。
**根因**：`FontFace.load()` 是异步的。
**修法**：`ensureFontLoaded(id)` → `clearTextCache()` → `buildLayout()` → `renderAt()`；导出前 `await ensureFontLoaded(scene.state.font)`。

### C3. 字体探测挡首屏
**症状**：首屏多 130 ms。
**根因**：对每个系统字族做 3 次 canvas 测量。
**修法**：先只列内置 5 款 + 通用族，`requestIdleCallback`（1200 ms 超时）再探本机字体。

### C4. 6.4 MB base64 写进 `<style>`
**症状**：HTML 解析 590 ms，FCP 2.6 s。
**根因**：CSS 解析器对每个 base64 URL token 做词法分析 + 字符串驻留。
**修法**：挪进 `<script type="text/plain">`，解析降到 32–51 ms，FCP 1.2 s。

### C5. 生僻字会回落
**症状**：龘靐齉爩𠮷 显示成方框或系统字体。
**根因**：子集只含 4191 字（GB2312 一级 + ASCII + 标点）。
**修法**：明确接受，按字体栈回落系统字体；不崩即可。

## D. 移动端与交互（8 条）

### D1. 页签条在脚本之后才解析
**症状**：`getElementById('mtab')` 拿到 null。
**修法**：改用文档级事件委托。

### D2. 自绘下拉被翻页容器裁切
**症状**：贴着页底时菜单只剩半截。
**根因**：`.pager` 有 `transform` + `overflow`，内部的 fixed 也会被裁。
**修法**：菜单挂到 `body`，`position:fixed`，按按钮 rect 定位。

### D3. 菜单点内部/滚动就关
**症状**：在菜单里滚动一下菜单就消失。
**根因**：`document` 的 click/scroll 监听没有排除菜单自身。
**修法**：`if(menu.contains(e.target)) return`；加 `overscroll-behavior:contain`（否则滚到底带动页面滚，又触发关闭）。

### D4. 同时能开多个下拉
**症状**：先开 MP4 再开 1080P，屏幕上两个菜单。
**根因**：关闭函数遍历 `.msel.open`，但引用挂在 `select.__msel` 上，`wrap.__msel` 是 undefined。
**修法**：补 `wrap.__msel = api`。
**判据**：连续开两个，`openCount === 1`。

### D5. 菜单里残留已删选项
**症状**：手机端菜单里还有 2K。
**根因**：先建自绘菜单、后删原生 `<option>`，菜单是快照。
**修法**：先改选项（删 2K、换短标签）→ 再 `buildNiceSelect`。

### D6. 自动降档不会触发 `change`
**症状**：程序把 1080P 改成 720P，自绘下拉还显示 1080P。
**修法**：赋值后手动 `syncNiceSelects()`。

### D7. 320px 下标签被截断
**症状**：「快速编码」显示成「快速编」。
**修法**：手机端换两字标签（快速/录制）。

### D8. 手机 1080P 导出崩溃
**症状**：中端机导出 1080P 时页面被杀。
**根因**：PCM + 视频分片 + 素材画布三项同时在线。
**修法**：三件套——① 先编音频、编完放 PCM；② 内存护栏 1200 MB；③ 预算模型按「PCM 全额 + 分片 50%」重算，超限先劝退。

## E. 性能（10 条）

### E1. 单级 rAF 等于白推
**症状**：想「先画首屏再干重活」，结果还是白屏很久。
**根因**：`requestAnimationFrame` 回调在**绘制之前**执行。
**修法**：两级 rAF；`renderAt` 里 `if(!assets.bg) return` 兜住。

### E2. 整宽 `backdrop-filter` 是滚动杀手
**症状**：滚动掉帧。
**根因**：sticky 页头每帧对整条宽度做 14px 高斯模糊。
**修法**：改 `rgba(...,.97)` 实色，视觉几乎无差。

### E3. 滑块每 input 全量重建
**症状**：拖一次字号，同步阻塞 1506 ms。
**根因**：每次 input 都 `buildLayout + renderAt`。
**修法**：合并到下一帧（`refreshPreview`），一次只重建一遍。60 次事件 → 0.7 ms。

### E4. 连续切页签排多个 rAF
**症状**：同一帧重绘多次。
**修法**：rAF 去重。

### E5. 每个下拉各挂 3 个文档级监听
**症状**：4 个下拉 12 个 scroll 监听，每次滚动全跑一遍并写 class。
**修法**：收敛成一套。

### E6. `renderAt` 冗余整屏底色
**症状**：1080p 每帧多一次全屏 fill。
**修法**：有 `assets.bg` 时不再铺底（buildBg 第一笔就是整屏不透明填充）。20 s 导出 10.9 → 10.7 s。

### E7. 双 VideoEncoder 并行没有收益
**实测**：2.51/2.48 s vs 2.61/2.44 s。
**原因**：核显只有一个编码引擎，两个会话排队。

### E8. 队列深度调参没有收益
**实测**：4 / 8 / 12 三档耗时在噪声内。背压只解决「不爆显存」，不是提速手段。

### E9. 让出策略没有收益
**实测**：all / 每 2 帧 / `time(12ms)` / 不让 —— 5.28 / 5.30 / 5.29 / 5.33 s，全等。
**结论**：`yieldNow` 保留是为了界面可交互，别指望它提速。

### E10. 可见性优化把录制画面冻住了
**症状**：兼容录制出来的片子画面全程定格，但时长和音频完全正常。停在预览页录一切正常，一滑到歌词区、或切到「样式」页再录，就必然静止。
**根因**：v59 为「屏幕外不烧 GPU」加的那道 `if(previewVisible) renderAt(t)`，恰好是录制链路**唯一的出帧口** —— `#cv` 一出视口就整段不重绘。音频走 `MediaStreamDestination`，与渲染无关，所以只有画面死，时长还被音频轨撑得好好的。
**修法**：`if(previewVisible || state.recording) renderAt(t)`；`renderAt` 记 `lastFrameAt`，录制计时器发现超过 800ms 没新帧就强制补一帧；录制中禁止切横竖版（`cv.width` 一变，`captureStream` 轨道立刻停帧，症状一模一样）。
**判据**：手机在「样式」页录一段，画面在动；非录制时切到「样式」页，canvas 仍不重绘（优化保留）。另实测 canvas 移到 `left:-6000px` 时 captureStream 照常出帧（1.3 s 内 40 帧、其中 39 帧互不相同），与视口内（37/40）一致 —— 2D 绘制不依赖元素可见性。

## F. 并发与异常（4 条）

### F1. 晚到的回调改新任务状态
**症状**：界面出现「文件下好了、状态是上一次的」；或新任务的 busy 被关掉。
**修法**：任务号 `beginJob()/jobOK()`；作废任务既不下载、也不改状态、也不碰 busy。

### F2. 异步导入竞态
**症状**：连续选两段音频，先选的大文件后解码完，覆盖了新选择。
**修法**：导入序号；音频有 3 个 `await` 点（量时长、metadata、decode），每个点都比对序号。

### F3. 异常未捕获会卡在「导出中」
**症状**：`captureStream` 在个别内核直接抛，按钮永远转圈。
**修法**：`exportRealtime` 整体 try/catch，异常时清定时器、置 busy/recording=false、hideBar、`keepAwake(false)`。

### F4. 老内核没有 `inert`
**症状**：导出中参数面板还能点。
**修法**：`.locked { pointer-events:none; opacity:.55 }` 兜底（Safari <15.5 / Firefox <112）。

## G. 测量工具本身的坑（5 条）

### G1. 窗口移到屏幕外会被判「被遮挡」
**症状**：同一段代码耗时忽高忽低（17/29/49 ms）。
**根因**：Chromium 节流合成器/GPU。
**修法**：加 `--disable-features=CalculateNativeWinOcclusion` + `--disable-backgrounding-occluded-windows`。

### G2. 用 DOM 里的画布建 VideoFrame 会走合成器读回
**症状**：单帧 200 ms。
**修法**：测编码必须用离屏画布。

### G3. headless 里 `captureStream` 帧率低
**症状**：录制时间被压缩，测出来的帧率不可信。
**修法**：帧率只能真机测；自动窗口只能验代码路径。

### G4. `canvas.toBlob` 在 headless 偶发不回调
**修法**：测试里改用 `toDataURL` 同步构造。

### G5. 中文文件名进 URL 要编码
**症状**：README 里链 `播放器视频生成器.html` 在部分环境 404。
**修法**：Markdown 链接用相对路径（GitHub 自动编码）；分享链接用 `%E6%92%AD...` 全编码形式。

## H. 发布与仓库（2 条）

### H1. 6.6 MB 单文件进 Git 会让 clone 变慢
**取舍**：不用 LFS（LFS 对普通访客不友好，还要额外配额）。6.6 MB 在可接受范围，但**不要再往里塞截图**——截图压成 JPEG（4 张共 0.9 MB）。

### H2. PAT 不能进仓库
**做法**：推送用环境变量传 token，不写进 remote URL、不写进脚本、不提交 `.git-credentials`。
**提醒**：任何贴到聊天/issue 里的 token 都应当作已泄露处理，用完立刻吊销重建。

## 附：三条「别再试」的总原则

1. **不要为了让数字好看去改时间轴**。时间戳是事实，压缩它一定换来音画不同步。
2. **不要相信能力查询**。`isConfigSupported` 只能当提示，真编一次才算数。
3. **不要在没有测量的情况下优化编码**。这个项目里 6 个「看起来该有效」的优化实测全为 0 收益（见 E7–E9）。
