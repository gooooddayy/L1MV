# 03 · 导出链路

导出是这个项目里最复杂、踩坑最多的部分。它要同时满足四个互相矛盾的要求：

1. **要真 MP4**（剪映、微信、相册都认）
2. **要快**（比实时快，最好 2×）
3. **不能中止**（缺素材、缺编码器、编码器报错都要继续）
4. **不能崩**（大文件、长音频、低端机）

一条链路做不到，所以有两条，外加四种兜底。

## 1. 总览

```
点「导出视频」
│
├─ 0. 预检 exportPreflight
│    ├─ 等字体加载完（否则整片按回落字体栅格化）
│    ├─ 解码音频（如果还没缓存 PCM）
│    ├─ 内存预算 memBreakdown → 超限直接劝退，说明该改哪个数
│    └─ 快照 scene = buildScene(K)   ← 之后改参数不影响这条
│
├─ 1. 快速编码（默认）
│    pickExportFormat → encodeMovie
│    ├─ VideoEncoder（H.264 / VP9 / VP8，硬件优先）
│    ├─ AudioEncoder（AAC 逐档试；全失败 → PCM）
│    └─ MP4.build（自写封装）
│
├─ 2. 兼容录制（快速编码不可用 / 用户主动选）
│    exportRealtime
│    ├─ pickMime（5 种 MP4 写法 → WebM）
│    ├─ canvas.captureStream(30) + 音频轨 → MediaRecorder
│    ├─ 出片是碎片 MP4 → remuxRecordedMP4（零拷贝重封装）
│    └─ 出片是 WebM → WEBM2MP4.convert()
│
└─ 3. 交叉兜底
     ├─ 快速编码抛「编码器初始化失败」且一帧没出 → 换下一个编码器 → 都不行则改录制
     ├─ 录制只出 WebM 且有 H.264 → 自动转 MP4/MOV，状态栏写「已自动转成 MP4」
     ├─ 没有 AAC 编码器 → 音频写 PCM，容器改 MOV
     ├─ 连 H.264 都没有 → 保留 WebM，但补齐 Duration 与 Cluster（能播、能拖）
     └─ 以上全失败 → 明确报错 + 释放 busy，可立刻重试
```

## 2. 快速编码

### 2.1 格式选择 `pickExportFormat(skip, ew, eh, brand)`

候选按「兼容性从高到低、画质从好到差」排：

| 顺序 | codec | 容器 | 说明 |
|---|---|---|---|
| 1 | `avc1.640028` | mp4 | High 4.0，1080×1920@30 刚好够 |
| 2 | `avc1.4d0028` | mp4 | Main 4.0 |
| 3 | `avc1.640032` | mp4 | High 5.0，老驱动更认这个 |
| 4 | `vp09.00.40.08` | webm | 没有 H.264 时的第一备选 |
| 5 | `vp8` | webm | 最后的兜底 |

每种编码器再按 `prefer-hardware → no-preference → prefer-software` 试一遍（有些驱动只在明确要求软件编码时才成功）。

**两轮循环**：先找「能带音频」的组合，实在没有再退成无声。因为「有音频却导成静音」是最难察觉的失败。

一个反直觉的点：**MP4 这条路不拿 `isConfigSupported` 当否决条件。** 很多安卓内核对 AAC 的支持性查询会误报（查询说没有，真编却有），一旦据此否掉 H.264，整条片子就掉成 WebM。所以这里只把它记成「预判提示」，真正决定 AAC 还是 PCM 的，是后面那次**真实编码**。

### 2.2 视频编码参数

```js
cfg = {
  codec, width: outW, height: outH,
  bitrate: clamp(w*h*30*bpp, 4e6, 24e6),
  framerate: 30,
  latencyMode: 'quality',
  hardwareAcceleration: 'prefer-hardware' | 'no-preference' | 'prefer-software'
}
```

- `bpp = 0.12`（桌面）/ `0.08`（手机）。1080p30 ≈ 7.5 Mbps，实测 0.12→0.08 只掉 0.3 dB PSNR（视觉无损），体积少 38%。
- 关键帧：`keyFrame: i % (fps*2) === 0`，即 **2 秒一个 IDR**，拖动进度不用解全片。
- 输出 chunk **立刻转 Blob**，把数据移出 JS 堆——长片不会把堆吃满。

### 2.3 音频

```
encodeAudioTrack(fmt, audioBuf, snapAudio, durSec, aFrom, aSpan, onProgress)
```

**探测**：`aacWorks()` 真编 4096 帧来判断。为什么不是 1024？因为 1024 帧时 `flush()` 会报「Flushing error」，那是探测方法的问题，不是设备的问题。

**逐档试**（从高码率到低码率、从 LC 到 HE-AAC 到 LD）：

```
mp4a.40.2 @ 192k → 128k → 96k
mp4a.40.5 @ 64k        （HE-AAC，部分内核只登记这个）
mp4a.40.29 @ 48k       （HE-AAC v2）
mp4a.40.1 @ 128k       （AAC-LC 别名）
```

有些安卓内核的 AAC 编码器挑码率（192k 直接拒绝、128k 能编），所以不能只试一次。

**全失败才退 PCM**：同一份解码样本改写成未压缩 16bit 小端 PCM（`buildPCMChunks`），容器改 MOV。宁可文件大，也不给无声片、也不掉成 WebM。

**手机先编音频**：`audioFirst = isPhone() && snapAudio`。编完立刻把 PCM 放掉（>120 MB 才放），峰值从「PCM + 视频分片」变成两者取大。

### 2.4 逐帧循环

```js
for (let i = 0; i < total; i++) {
  if (state.cancel) throw new Error('已取消');
  if (encErr) throw encErr;

  const frame = withScene(scene, () => {
    renderAt(i / fps);
    return new VideoFrame(cv, { timestamp: i*1e6/fps|0, duration: 1e6/fps|0 });
  });
  venc.encode(frame, { keyFrame: i % (fps*2) === 0 });
  frame.close();

  while (venc.encodeQueueSize > 4) await yieldNow();   // 硬背压
  if ((i & 31) === 0 && performance.memory) { /* 内存护栏 */ }
  if (i % 3 === 0) onProgress(...);
  await yieldNow();                                     // 每帧让一次
}
await venc.flush();
```

四个刻意的设计：

| 设计 | 原因 |
|---|---|
| `withScene` 包住渲染 + 建帧 | 中间没有 `await`，不会和界面绘制串台 |
| 在飞帧 ≤ 4 | 一次怼几百帧进队列会爆 GPU 内存（Chromium #40944632） |
| 每 32 帧查堆 | 预算是开跑前算的，这条是运行中兜底；超 1200 MB（手机）/ 2600 MB（PC）主动停 |
| 每帧 `yieldNow()` | 界面能点、能滚、能改参数；实测对总耗时无影响（四种让出策略耗时全等） |

> 内存护栏在 Safari / Firefox 上直接跳过——它们没有 `performance.memory`，硬查会误报。

### 2.5 封装 MP4

自己写的 `MP4.build()`，box 树：

```
ftyp
moov
 ├─ mvhd
 ├─ trak (video)
 │   ├─ tkhd
 │   └─ mdia
 │       ├─ mdhd
 │       ├─ hdlr
 │       └─ minf
 │           ├─ vmhd
 │           ├─ dinf/dref
 │           └─ stbl
 │               ├─ stsd → avc1 → avcC
 │               ├─ stts  ← 逐样本时长
 │               ├─ stss  ← 关键帧索引
 │               ├─ stsc / stsz / stco
 ├─ trak (audio)
 │   └─ … stsd → mp4a → esds   或   sowt（PCM）
 └─ udta → ©nam / ©ART
mdat
```

三个关键点：

1. **`stts` 必须按每帧真实时长写**。写死 1/30，VFR 素材会把 4 分钟的片子压成 2 分 50 秒（比例 0.686）——这是 v51 的真凶。
2. **AAC 有 priming**：Chrome 会额外加 2–3×1024 个样本，容器时长虚高 60–80 ms。用 `elst`（edit list）把音频起点往后推，音画才对得上。
3. **PCM 用 `sowt`**（16bit 小端），并且**只在 MOV 品牌下用**。mp4 + sowt 在 Chrome 能播，但 `decodeAudioData` 解不出，手机相册和电视更不保证——不赌。

`©nam` / `©ART` 写歌名与歌手，剪映和播放器会显示。

### 2.6 收尾

- 编码错误可能在 `flush()` 之后才出现，且会被 `close()` 吞掉 → 出片后校验帧数与时长。
- `disposeScene()`：画布置 1×1、释放布局；K≠1 时清字形缓存。
- 成功后才调 `beginJob` 对应的下载；任务号不匹配的回调直接丢弃。

## 3. 兼容录制

### 3.1 容器选择 `pickMime()`

按顺序试 5 种写法，全不行才退 WebM：

```
video/mp4;codecs=avc1.42E01E,mp4a.40.2
video/mp4;codecs=avc1.4D401E,mp4a.40.2
video/mp4;codecs=h264,aac
video/mp4;codecs=avc1
video/mp4
→ video/webm;codecs=vp9,opus → video/webm
```

早期只试 2 种就放弃了，结果一批安卓机永远拿不到 MP4。

### 3.2 录制

`cv.captureStream(30)` + 音频轨（`AudioContext.createMediaStreamDestination`）→ `MediaRecorder`。

录制是**实时**的（1× 速），且必须保持页面在前台。手机端录制期间申请 `wakeLock`。

### 3.3 切走即停，不做暂停续录

`MediaRecorder.pause()/resume()` 不补偿时间戳，实测少 1.2–1.5 秒，回来必漂移。所以切走就停止并保存已录部分，状态栏说明「已停止（切走了）」。

### 3.4 重封装 `remuxRecordedMP4(bytes, meta, collect, srcBlob)`

MediaRecorder 写的是**碎片 MP4**（边录边写，moov 在前、多个 moof），很多播放器不认。做法是解析 `stbl` 重封装成规整 MP4。

内存是这里的坑：老写法「原数组 + 每帧 new Blob 复制 + 最终 Blob」三份并存，4 分钟 1080p（约 210 MB）峰值 600 MB+。改成 **`srcBlob.slice()` 零拷贝**（Blob 切片共享底层数据），封装前把解析数组置空，峰值降到约两份。

## 4. WebM → MP4 / MOV

只在「录制只能出 WebM」的设备上走这条路（PC 和新版 Chrome 直接出 MP4，根本不进）。

### 4.1 自写 EBML 解析

```
EBML 头 → Segment → Info / Tracks / Cluster
只取 SimpleBlock 与 BlockGroup 里的 Block
```

三个必须知道的坑：

| 现象 | 根因 | 修法 |
|---|---|---|
| 「WebM 开头没有关键帧」 | Chrome 把视频帧写成 **BlockGroup**，Block 的关键帧标志位不填 | 按 Matroska 规范：**没有 ReferenceBlock 就是关键帧** |
| `Invalid coded size (0,0)` | 宽高/采样率藏在 `Video(0xE0)` / `Audio(0xE1)` 子元素里，第一层 TrackEntry 是空的 | 下钻一层读 |
| 只转了第一个 cluster（6s 只出 3.35s） | Cluster 长度是「未知」（`0x01FFFFFFFFFFFFFF`），解析器当成「到文件末尾」 | 外层 `end` 改 `let` 且允许回缩；遇到下一个 Cluster 头（`0x1F43B675`）或未知长度子元素就 `end = cp` 提前收尾 |

### 4.2 色彩范围

VP9 是全范围，`VideoDecoder` 默认按有限范围报，`drawImage` 时被压一次（`#112233` → `#011628`）。`configure` 里显式 `colorSpace: { fullRange: true }` 才对得上（源 16,35,51 / 成片 16,35,52）。

### 4.3 帧时长（VFR）

`vChunks` 只有时间戳没有每帧时长，封装时会一律按 1/30 写 `stts`。录制是 VFR，手机跑特效只有 ~20 fps：音 248 秒、视频按 30 fps 重排成 170 秒（2:50）。

修法：编码完成后按相邻时间戳补 `d = round(Δt × 0.09)`（µs → 90 kHz），最后一帧 +33 ms。实测 20 fps / 7.9 s 的 WebM：修前视频轨 5.07 s，修后 **7.93 s**，音频 7.94 s。

### 4.4 音频起点对齐

以画面第一帧为 0：音频晚 `headPad` 就补静音，早 `-headPad` 就裁掉；中途丢包（时间戳跳变 > 3 ms）也补静音。

### 4.5 双趟编码

```js
runPass(usePCM)
```

先试 AAC；抛错或没出帧，整趟重跑 PCM。避免出现「半条无声片」。

### 4.6 `fixWebm()`

MediaRecorder 的 WebM 没有 Duration（`duration = Infinity`），播放器显示 0、拖不动。做法：EBML 头与 Tracks 原样搬运，重写 Info（TimecodeScale + Duration + 应用名）与每 1 秒一簇的 Cluster（相对时间戳 int16）。

实测 6 s 录制：修前 Infinity，修后 **6.02 s / 640×360 / 可拖到 3.0 s / 可播放**，耗时 ≈ 0。

### 4.7 闸门

| 闸门 | 阈值 | 行为 |
|---|---|---|
| 转码 | 文件 > 300 MB | 跳过，提示「太大，建议用电脑导出」 |
| 补时长 | 文件 > 400 MB | 跳过，提示「太大没补时长索引」 |

## 5. 兜底矩阵

| 设备能力 | 快速编码 | 兼容录制 | 最终产物 |
|---|---|---|---|
| H.264 + AAC（绝大多数） | ✅ | ✅ | MP4（H.264 + AAC） |
| H.264，无 AAC（部分国产内核） | ✅ | ✅ | **MOV**（H.264 + PCM），状态栏说明原因 |
| 无 H.264，有 VP9 | ✅ | 仅 WebM | WebM → 自动转 MP4（有 H.264 时）/ MOV |
| 无 WebCodecs（旧 Safari） | ❌ | ✅ | 录制 MP4（Safari 只支持 mp4） |
| 仅 WebM 录制（Firefox） | ✅（桌面 130+） | ✅ | WebM → MP4 |
| 什么都没有 | ❌ | ❌ | 导出按钮禁用 + 说明缺什么 |

## 6. 时长与同步

| 问题 | 做法 |
|---|---|
| 音频时长不准 | **不信文件头**，以解码后的样本数为准（VBR MP3 的头常差 1–2 秒，导致成片尾部多出等长静音） |
| 导出片段 | `aFrom` / `aSpan` 支持只取音频的一段（试听/切片） |
| AAC priming | `elst` 校正 |
| 录制热身 | 开头 0.4–0.5 s 静止，属已知取舍（裁掉会切走关键帧） |
| 音轨起点 | 以视频第一帧为 0，补静音或裁剪 |

## 7. 取消与失败语义

- **取消**：`state.cancel = true` → 循环里抛 `已取消` → 不下载、不写成功状态、释放资源；日志记「用户取消」。
- **失败**：必须复位 `busy / recording / 进度条 / 遮罩`，否则界面永远卡在「导出中」。
- **晚到的回调**：任务号不匹配 → 不下载、不改状态、不碰 busy。
- **部分失败**：音频编不进去 → 无声片 + 说明；视频编码失败 → 换编码器重试 → 再不行改录制。

## 8. 已知限制

| 限制 | 原因 |
|---|---|
| 录制全片只有 1 个 IDR | MediaRecorder 固有，不重编码无解 |
| 录制开头 0.4 s 静止 | 起录热身 |
| 手机录制 17–29 fps | 1080P + 特效全开的实际渲染能力 |
| 60 分钟长片未实跑 | 有预算拦截 + ETA，属已知边界 |
| 2K 以上分辨率 | 浏览器编码器扛不住 |
