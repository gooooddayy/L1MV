## 原文（2026-10-29 起，按时间顺序）

## 剪映·音乐播放器 CD 弹出效果方案（完成）
- 需求：分析一张播放器成片截图（某流行歌曲），拆解元素与效果，输出完整制作方案。
- 交付物：`音乐播放器CD弹出效果_完整制作方案.html`（零依赖单文件，10 个区块：拆解表 / 图层栈 / 时间轴 / 9 步制作 / 关键帧表 / 参数表 / BPM 计算器 / 效果复现 demo / 排错 / 变体）。
- 核心技术判断（后续复用）：
  - 该效果本质是「一图三用」：主轨道压暗 60% 作背景、画中画 1:1 作封面卡、复制画中画加圆形蒙版作 CD。
  - 机关在层级：CD 与圆环贴纸必须置于封面卡**之下**（不是全局最底），靠遮挡产生"抽出来"错觉。
  - 弹出位移取 CD 直径 72%（露出约 2/3 圆面），圆环贴纸才会完整；位移 64% 时圆环会被卡片切掉一半。
  - 旋转角度按 BPM 算：圈数 = 时长 × BPM / 60，每 2 圈补一个线性关键帧，防剪映走最短路径。
  - 剪映「蒙版圆角」是 0–100 相对值，20 ≈ 短边 10%。
  - LRC 导入若生成文本层，做色度抠图会整层消失；只有绿幕歌词素材才需抠像。
- 验证方式：Edge `--headless=new --screenshot` + 注入 CSS 隐藏其他 section 做分区截图（注意 virtual-time-budget < 4s 容易截到空白，用 12s 以上稳定）。

## 播放器视频生成器（网页版，已跑通）
- 文件：`L1MV.html`（单文件零依赖，本地不上传）。
- 链路：上传封面图 + LRC/TXT + 可选音频 → Canvas 2D 逐帧合成 1920×1080 → `captureStream(30)` + `MediaRecorder` 录 WebM(VP9/Opus, 12Mbps) → 自动下载。
- 关键实现：
  - 静态层预渲染（背景虚化 / 唱片纹路 / 卡片 / 倒影 / 暗角）只算一次，每帧只做贴图+文字，1080p 单帧 <8ms。
  - 时间轴：0–0.85s 缩放入场（**不要用 globalAlpha 做入场淡入**，会让卡片半透明露出后面的唱片），0.95–1.77s 位移 72%，1.7s 起按 RPM 匀速旋转。
  - 音频必须走 `AudioContext.createMediaElementSource` → 同时接 `destination`（预览）与 `MediaStreamDestination`（录制）；**MediaElementSource 每个元素只能创建一次**，重复载入音频要复用 srcNode，否则 InvalidStateError。
  - LRC 读取用 TextDecoder UTF-8 fatal，失败回退 GBK（Windows 记事本常见）。
  - 首句歌词之前 `activeIndex` 返回 -1，要兜底成 0，否则画面无歌词。
- 实测（Edge headless）：8 行歌词解析正常、录制 2.2s 出 6 个 chunk / 1.16MB，录制链路可用。

### v2 升级（同日）：横竖双版 + 离线导出 + 质感重做
- **横竖双版**：`LAYOUTS.landscape / portrait` 两套坐标，`applyLayout()` 切 W/H、重建素材、设 canvas 尺寸（1920×1080 / 1080×1920）。默认横版。
- **离线导出（关键）**：WebCodecs `VideoEncoder`(VP9) 逐帧编码 + **自写 WebM 封装器**（EBML/vint/SimpleBlock/Cluster），比 MediaRecorder 实时录制自由；失败自动回落实时模式。
  - 封装要点：Segment 用已知 size（先算 body 长度）；Cluster 按 4s 切；SimpleBlock 相对时间 int16 BE；Opus 需 `CodecPrivate`=OpusHead + CodecDelay/SeekPreRoll；TrackType 1=video 2=audio。
  - 音频：`OfflineAudioContext(2,48000,48000).decodeAudioData` 强制重采样到 48k，再按 960 帧喂 `AudioEncoder`(opus)。
  - 编码参数用 `latencyMode:'realtime'` 明显快于 'quality'。
- **实测速度**（无 GPU 的 headless）：1080p 约 45–52ms/帧，接近 1×；有硬件编码时更快。不要宣称"2–6 倍"。
- **质感**：黑胶=深色盘体+中央 0.81R 画面+纹路+细高光边；卡片=双层预渲染阴影（tight/wide）+ 1.5px 玻璃边；唱片背后加柔光把深色盘体托出背景；背景用封面主色 soft-light 调色。
- **歌词滚动**：按「换行瞬间 t-cur.t 的 0~0.5s 内 smoothstep 上滚」驱动，当前行恒居中；**不要用"下一句前 30% 预滚动"**，会出现高亮句偏上。
- **验证方法（重要）**：headless 下 `--virtual-time-budget` 会让 WebCodecs 卡住/时间失真，必须用 CDP（Node 内置 fetch + WebSocket，`--remote-debugging-port`）跑 `Runtime.evaluate(awaitPromise)` 做真实等待。容器正确性用 `MediaSource.addSourceBuffer('video/webm; codecs="vp9,opus"')` + `appendBuffer` 看 buffered 区间即可验证。

### v3 升级（同日）：歌词编辑器 + 主色提取 + 高级光影
- **歌词编辑器**：预览下方可编辑表格（时间 mm:ss.cc / 文字 / ◉取当前时间 / 删除），改文字即时重排并刷新预览；导出 LRC。编辑时间后必须 `state.lyrics.sort()`，否则 activeIndex 的二分查找会失效。
- **主色提取**：sRGB→Oklab 做 K-means（直方图取种子保证确定性，12 轮），权重 = 中心加权 × 饱和度加权 × **中间调优先**（`exp(-((L-0.56)/0.30)^2)`，没有这一项会被大块暗部主导，整页发黑）。剔除 L<0.10 / >0.97；背景 `baseL=clamp(dom.L*0.70,0.26,0.44)`，`deep=baseL-0.22`，保证亮暗层次；强调色色度不足时用主色相补 0.08。
- **光影**：卡片呼吸光晕（sin 0.52）+ 8.5s 一次的对角玻璃扫光 + 顶部轮廓光；唱片用**缓旋转的线性高光**（t*0.26）；浮尘 20 粒（预渲染 sprite）。全部走 `state.light` 开关。
- **踩坑**：`createConicGradient` 做唱片高光会出现硬边扇形，像切开的披萨，改用旋转线性渐变。
- **用户明确要求**：标题不加书名号；唱片**不要中心轴孔**（1080p 下就是一个突兀黑点）；转速默认 **15 rpm**（33⅓ 太快）；**底部只显示进度条**，五个控制图标去掉。

### v5（同日）：歌词逐行编辑回归 + 柔边

### v8（同日）：特效精简 + 单滑杆 + B 方案自定义叠加
- **特效清单精简为 4 项**：水滴涟漪(on) / 光斑浮动(on) / 胶片颗粒(off) / 光带扫过(off)。删掉细雨斜丝、暗角（暗角改为 `buildVignette` 里以 .20 常驻烘焙进背景，注意 buildVignette 在 buildBg 之后调用，要自己贴到 `assets.bg` 上）。
- **单滑杆交互**：点特效名字 `fxSel` 选中（行高亮 + 名字变蓝加粗），下方 `.fx-ctl` 一根滑杆调该项强度，标题显示「强度 · 某某」；开关切换也会自动选中该项。行结构改成 `span.fx-name` + `label.sw`，否则点名字会误触开关。
- **B 方案（自定义叠加）**：`overlays[]`，每个 = `{frames:[ImageBitmap], dur, blend, alpha, on}`。

### v9（同日）：封面卡「灰色半透明底盘」+ 唱片外扩暗环
- **卡片改成双层**：`assets.cardPlate`（比图片大 4.2%，圆角 R+M*0.85，白色渐变 alpha .19→.075，1.4px 高光边，feather 7px）+ `assets.card`（图片，feather 从 12px 降到 1.2px，边缘清晰，另加 1.2px 内描边）。绘制顺序：光晕 → 阴影 → 底盘 → 图片。
- **踩坑**：`buildCard` 切片边界必须用 `function buildReflect(){`，用 `drawReflection` 会把后面十几个函数一起吞掉（drawReflection 定义在 buildCard 之后）。
- **唱片**：外圈 destination-out 从 .46 收到 .24（保住清晰轮廓），另加半径 1.085k 的深色半透明环（α .40→0）当「比盘面大一圈的底盘」，feather 4px；中央画面内压边 .30 → .17，圆面边缘更干净。
- 像素验证：一行扫描得到 art 右沿 825、黑胶右沿 875，差值 50 ≈ 0.24k，与 ar=0.76k 吻合，说明封面圈与黑胶同心且比例正确。
- **v9.1 修正**：用户指出「图片上层的透明层比图片小」。根因是 `drawCard` 里两块光效（扫光、顶部轮廓光）的裁剪矩形各自内缩了 5px / 6px（`rr(ctx, x+5, y+5, s-10, s-10, r-5)`），在图片内部留下一个「小一圈」的亮边。改为 `rr(ctx, x, y, s, s, L.card.r)` 后消失。底盘透明度同步提到 .24/.155/.10。**教训：凡是覆盖在贴图上的光效，裁剪必须用与外层完全相同的路径，不能为了「避开羽化边」而内缩。**
- **v9.2**：用户反馈「圆形的这个好像不见了」= 唱片在深色背景上失去圆形轮廓。原因：v9 把盘缘 destination-out 透明化从 .46 降到 .24、又加了一圈暗环，同时原来那圈 rim 高光只有 α.30/.06/.16、宽 0.9px，几乎看不见。修法：① 暗环半径 1.085k→1.06k、α .40→.26；② 盘缘内侧加 `k*0.90→k` 的 accent 径向渐亮（α 0→.20）；③ rim 描边提亮到 α .62/.22/.40、宽 1.4px；④ 封面圈与黑胶的分界线 α .10→.16。
- **时长优先级（现行为，回答用户提问时已确认）**：有音频 → 音频时长直接覆盖总时长，此时「总时长」输入框被 `if(state.audioReady) return;` 挡住；无音频 → 总时长 = max(默认16s, 手填, 最后一句+4)；纯 TXT 无时间轴按当前总时长均分。歌词滚动完全由 LRC 时间戳 + offset 决定，与 rpm 无关。

### v18（同日）：导出管线重构（MP4 / 速度 / 稳定性 / 输入兼容）
- **导出方式盘点（改前）**：① 快速＝WebCodecs VP9 12Mbps + 自建 WebM 封装；② 兼容＝MediaRecorder 实时录制。问题：只能出 WebM、VP9 纯软件慢、码率写死、所有分片以 Uint8Array 堆在 JS 堆（3 分钟≈270MB）、`sleep()` 在后台标签页被压到 1s/次。

### v30（10-30）：续播接缝 + 录制期全控件锁定 + 中断语义闭合
**问题一「续播会不会跳」——之前会，现在不会**：实测暂停空档被 MediaRecorder 录成一个 735–1162ms 的超长帧（画面卡一下）。修法两层：① `fixDurs()` 在重封装时把 >150ms 的异常长样本压回正常帧长（正常 VFR 抖动不动）；② 暂停时画面+音频一起停，内容本身连续。最终实测 `big: []`（无长帧）、154 帧/5.23s（5s 内容+0.23s 尾）、进度条反推内容时间轴斜率 0.99 平滑 1:1。

### v32（10-30）：按 v31 排查结果修复（时长死锁 / 多声道 / 预算 / 录制）
1. **解死锁**：新增 `SAFE_DUR = 900`。`applyDuration()` 改为「填了就以填的为准（可长可短），没填就取 `min(基准, SAFE_DUR)`」，删掉 `durManual <= durBase → null` 这条重置。`inDur` 的 max 900→7200。实测：60 分钟音频 → 默认 900；手填 600 生效；手填 3600 生效并**开始导出**（提示「成片预计 3.3 GB」）；填 7200 被拦但提示「改到 60:00 以内」＝可自救。
2. **多声道下混**：`encodeMovie` 音频循环前按 `numberOfChannels` 推断布局（3ch=L R C / 4ch=L R Ls Rs / 5ch=L R C Ls Rs / ≥6ch=L R C LFE Ls Rs[+Lss Rss]），`L = FL + 0.707*(FC+BL+SL)`、`R` 同理，LFE 不混入（与浏览器播放一致），逐块混并 clamp。实测：6ch 仅中置 → L/R 各 0.249（期望 0.25）；4ch 仅左后 → L 0.249 / R 0（旧版是 0）；3ch 仅中置 → L/R 各 0.249。

**回归**：立体声 RMS 0.282（期望 0.2828）、录制 2.45s/1920×1080/可拖进度、竖版 2K 1440×2560、纯歌词默认 34.3s（末句+4 未受影响）、无音频 memMB 41。

### v33（10-30）：录制裁剪对齐关键帧 + 默认全长 + 剩余时间
1. **录制裁剪的致命 bug（用户反馈「前 3 秒有音频没画面、拖不进去」）**：v30 的 trimList 按样本时长硬裁，没管关键帧 —— MediaRecorder 的 IDR 间隔有几秒，裁掉开头就丢了唯一解码起点，播放器只能跳到下个 IDR（约 3 秒），这段也拖不进去。修法：裁剪点先算到 trimMs，再**回退到最近的 keyframe**；落不到（keyframe 在 0）就 cut=0 不裁；音频按视频实际裁掉的 cutMs 对齐。实测修复后：dur 7.38、`seekable [0, 7.38]` 全段、每个 seek 点 lit 0.98 有画面。
   **代价**：短视频的关键帧就在 0，裁剪退不上去 → 成片保留约 0.4–0.5s 的「第一帧静止」预热段，总长比设定多 0.4s。像素比对证实成片第 T 秒 ≈ 预览第 T-0.5 秒（bestOff=-0.5）。这是「能解码」换来的，比黑屏 3 秒好。
2. **默认时长回到全长**：`applyDuration` 去掉 `min(base, SAFE_DUR)`，改回 `durBase`；`SAFE_DUR` → `LONG_DUR`（只作提醒阈值，不再截断）。实测 60 分钟音频 → duration 3600、输入框 3600。
3. **剩余时间**：编码进度条 `视频编码 42% · 还剩 01:12`，用最近速度指数平滑（0.55/0.45）而非全程平均（全程平均在 7% 时估 25s，实际 4.7s；改后估 17s→7s→4s 收敛）。录制进度条同样加「还剩」。`eta < 1s` 或 `p > 0.97` 不显示。
4. **内存提醒**：导入时 `estAudioMemMB() > 800` 才提醒（约 35 分钟立体声），正常歌曲不打扰；导出中状态栏追加「音频占 X MB 内存」并转 warn。录制模式不提醒内存（它没有 PCM 成本）。

### v35（10-30）：切页面音画漂移的真凶 = fixDurs
**用户反馈**：录制 27fps、4:03（编码 4:06），中途切页面后「越到后面音频跟歌词对不上」。
**实测两轮**：
1. `pause/resume` 版本：暂停 3 秒后 视频轨 11.371s / 音频轨 12.868s（差 1.5s）；音频滴答间隔 1.00 均匀 → 音频连续，是**视频轨迹短了**。
2. 试了「切走 stop、回来新建 recorder、最后 concat 样本」的分段拼接：拼接本身成功（2 段已合并），但**每段新建录制器都要重新预热**，12 秒内容只录出 7.454s 视频（164 样本）/ 13.32s 音频，接缝处音频还有 1.47s 间隙 → **方案否决，已回退**。
3. 回退后定位到真凶：**`fixDurs()`**。它把「超过中位数 3 倍或 150ms」的帧一律压回中位数。录屏在低帧率环境常产 100–200ms 的长帧，被压成 33ms 后**视频时间轴整体缩水**（实测 3.46s → 1.84s），而音频不压 → 音画越走越偏。这条规则是 v30 为「暂停产生的 1.1 秒超长帧」加的，现在暂停走 pause/resume 不再产超长帧，已移除。
**另外修**：`recTimer` 在内容起跑前（recContentStart=0、baseTime 未设）会把 currentTime 算成巨值，误判「已播完」→ 加 `recContentStart &&` 守卫；`currentTime()` 加 `Math.max(0, ...)`。
**同时移除**：预热段裁剪（`trimMs` 恒传 0）——它要么落不到 IDR 导致开头不可解码，要么把开头整秒内容切掉。现在接受成片开头约 0.4s 静止，换「内容一秒不少、全段能拖」。
**修复后实测**：不切页面 3 秒内容 → 3.45s（原始 3.46s，重封装无损）。切页面仍有 1.18s 视频时间轴缺口（MediaRecorder pause/resume 的固有缺陷，待定方案）。

### v36（10-30）：兼容录制改为「切走即停止」
- `visibilitychange` 从「暂停/续录」改为「直接 endRealtime 并保存」，用 `recStopWhy='hidden'` 三态文案（`已停止（切走了）`）。

### v38（10-30）：导出提速专项 —— 实测结论：已到硬件天花板
用 CDP + 真实 GPU（Intel HD 630）在页面内做拆解测量（工具在 `.workbuddy/bench/`，`run.mjs` 启动 Edge + `bench-*.js` 在页面里跑）：
- **渲染 + 取帧**（离屏画布，`renderAt` + `new VideoFrame`）：**8.1 ms/帧**
- **编码器空转**（静态画布预热后）：**11.6 ms/帧 = 86 fps**（avc1.640028 硬编）
- **合起来真实导出**：17–21 ms/帧（≈50–59 fps），约等于两者相加 —— 渲染与编码在**同一颗 GPU 上排队**，没有重叠空间
- 4 分钟音频编码 4.5 s（占全长 2%）
**试过但无效（别再试）**：
1. 双画布交替（想让渲染与编码并行）：同会话交替 6 次，双 6.95/7.42/7.10 vs 单 7.43/7.43/6.83 —— **无差别**。之前看到的「1.6×」是小样本噪声，已回退。
2. 队列深度 4/8/12：6.32/6.25/6.18 与 6.24/6.22/6.13 —— 无差别（编码器本来就追得上）。
3. `alpha:false` 不透明画布：反而 49 ms/帧（触发慢路径），已回退。
4. 强制软件编码（OpenH264）：5.78/6.09 vs 硬件 5.12/5.24 —— 硬件更快，已否决。
**保留**：`renderAt` 去掉多余的一次 `clearRect`（全屏写入，底色已盖满）。
**测量坑**：窗口移到屏幕外会被 Chromium 判「遮挡」→ 合成器节流，耗时忽高忽低（17/29/49ms）；须加 `--disable-features=CalculateNativeWinOcclusion`。另外**必须用离屏画布**测编码：拿 DOM 里的 #cv 建 VideoFrame 会走合成器读回，单帧 200ms。
**结论**：这颗 iGPU 的编码器 86fps 是硬上限，渲染再省最多也只能快 1.4×。要更快只能减帧数（25fps −17%）或降分辨率。

### v47（10-31）：WebM 录制自动转 MP4（只对「录不出 MP4」的设备生效）
**触发条件**：`finalizeRecording` 里 `ext === 'webm'` 才走，PC 与新版 Chrome 录制直接出 MP4，根本不进这段。文件 >300MB 或缺少解码/编码能力时跳过并说明。
**实现**：`WEBM2MP4`（放在 MP4 封装器之后）
1. 自写 EBML 解析：EBML 头 → Segment → Info/Tracks/Cluster；只取 SimpleBlock / BlockGroup 里的 Block。
2. `VideoDecoder(vp8|vp09.00.10.08)` + `AudioDecoder(opus)` 解，`VideoEncoder(H.264，用 pickExportFormat 选的配置)` + `AudioEncoder(AAC 192k)` 重编，最后 `MP4.build` 出片。
3. 解码一帧→编码一帧（队列背压 8/4），不把整片帧堆内存。
**三个坑（都实测踩过）**：
- Chrome 把视频帧写成 **BlockGroup**，Block 的关键帧标志位不填 → 必须按 Matroska 规范「没有 ReferenceBlock 就是关键帧」判断（否则「WebM 开头没有关键帧」）。
- 宽高/采样率/声道在 **Video(0xE0) / Audio(0xE1) 子元素**里，第一层 TrackEntry 上是空的（`Invalid coded size (0,0)`）。
- **色彩范围**：VP9 是全范围，`VideoDecoder` 默认按有限范围报，`drawImage` 时被压一次（#112233 → #011628）。configure 里显式声明 `colorSpace:{...,fullRange:true}` 后一致（源 16,35,51 / 成片 16,35,52）。
**实测**：4 秒 VP9+Opus → MP4，`avc1/mp4a/moov/mdat` 齐全，时长 0.37s 对应 11 帧、像素与源一致、转换耗时 0.6s。快速编码路径未受影响（0.7MB/2.5s）。

### v48（10-31）：帧率判定 + 状态文案复位 + WebM 转 MP4 的致命截断修复
**用户反馈**：① 4:07 的录制片只有 28.85 帧/秒；② 上一条结果文案（已停止（切走了）…）在下次导出时还挂着；③ 手机端导出仍是 WebM。
1. **帧率是判据不是目标**：录制是实时抓帧 VFR，`captureStream(30)` 靠合成器采样，偶尔两个 tick 落在同一次绘制上就少一帧。247s × 28.85 ≈ 7126 帧，理想 7410，少 3.8%（上次同机 29.45 = 少 1.8%，随机器负载浮动）。时间戳是绝对的，音画仍同步 → 正常。低于 27（≈10%）才需要担心。**别用自动窗口测帧率**：窗口不聚焦时 captureStream 只有 ~27fps，且 MediaRecorder 时间被压缩（实测 6.01s 只录出 5.98s，还可能更少）。
2. **结果文案不实时**：`#status` 只有失败/成功时才写，录制全程留着上一次的「已停止（切走了）· …」。修：点导出立刻 `setStatus('准备导出…')`；`exportRealtime` 开头 `setStatus('录制中…')`。
3. **WebM→MP4 真 bug（严重）**：MediaRecorder 写出的 Cluster 是**未知长度**（0x01FFFFFFFFFFFFFF）。解析器把未知长度当成「到文件末尾」，于是第二个 Cluster 只在头部被看到就 break → 只转了第一个 cluster。实测 6s 录制：修前 86 块 / 3.35s，修后 165 块 / 5.98s；10s 录制转出的 MP4 从 0.37s 变成 9.3s。修法：外层 `end` 改为 `let` 并允许回缩，cluster 内遇到 0x1F43B675（下一个 Cluster 头）或未知长度子元素就把 `end = cp` 提前收尾，`pos = end` 继续下一个。
4. **「为什么还是 WebM」不再沉默**：新增 `WEBM2MP4.blockReason()`，返回人话原因（缺视频/音频解码、音频编码、AAC、H.264 各一种说法）。录制前就问一次并写进状态栏；出片后的 note 里也带这句，且不再重复通用的 webmNote。
**实测**：390 与 1440 视口导出正常；模拟「只能录 WebM」→ `已导出 MP4 1280×720 · 0.8 MB · 已自动转成 MP4`、文件名 `.mp4`；模拟「无法转码」→ 状态栏直接说明缺哪项能力，文件名仍 `.webm`。

### v49（10-31）：无 AAC 设备不再降级成 WebM（PCM 音轨）+ 录像内存 + WebM 补时长
**用户反馈**：① PC 录像导出崩过一次；② 手机导出 WebM 放不了、时长 0，提示「没有 AAC 编码」；③ 手机快速编码也变 WebM，「越改越差」。
1. **根因（②③同源）**：那台手机的浏览器**没有 AAC 编码器**（国产内核常把 AAC 裁掉）。`pickExportFormat` 一旦发现「要带音频但 AAC 不支持」就跳过所有 avc1 候选 → 退到 VP9/VP8 → 整条片子变 WebM。录制那条更惨：录制器又只能录 WebM，于是永远拿不到 MP4。
2. **PCM 音轨（核心修复）**：MP4 只认 AAC，但 **PCM 不需要编码器**。给封装器加了 `'sowt'`（16bit 小端未压缩）采样条目 + `audioPCM` 选项；`buildPCMChunks()` 直接把解码后的样本写进去（下混规则与 AAC 那条完全一致，LFE 不混）。
   - 快速编码：`pickExportFormat` 在「AAC 不可用」时不再跳过 avc1，而是标记 `audioPCM`、品牌改 `mov` → 输出 **MOV（H.264 + PCM）**，扩展名自动 .mov。
   - 录制转换：`convert()` 里 AAC 不可用时走 `flushPCM()` 累积写 PCM，同样出 MOV。
   - `blockReason()` 不再因为没 AAC 拦人；新增 `willUsePCM()` 供文案判断。
   实测：模拟无 AAC → `已导出 MOV 1280×720 · 1.4 MB · 音频以未压缩 PCM 写入`，Chrome 解码回 3.00s / 2ch / peak 0.275；WebM→MOV 转换 4s 片子 dur 3.96、音频 3.96、peak 0.254。
3. **PC 录像崩溃**：`remuxRecordedMP4` 老写法是「原数组 + 每帧 new Blob 复制 + 最终 Blob」三份内存，4 分钟 1080p（约 210 MB）峰值 600 MB+。改为 `srcBlob.slice()` 零拷贝（Blob 切片共享底层数据），并在封装前把解析数组置空 → 峰值降到约两份。参数新增第 4 个 `srcBlob`，调用处传入原始录制 Blob。
4. **WebM 放不了（时长 0）**：MediaRecorder 边录边写，Segment/Cluster 长度是「未知」、Info 里没有 Duration → 播放器读到 `duration = Infinity`（实测原始文件确实 Infinity）。新增 `WEBM2MP4.fixWebm()`：EBML 头与 Tracks 原样搬运，重写 Info（TimecodeScale + Duration + 应用名）与每 1 秒一簇的 Cluster（相对时间戳 int16）。实测 6s 录制：修前 Infinity、修后 **6.02s / 640×360 / 可拖动到 3.0s / 可播放**，耗时 ≈0。
   转不了 MP4 时也会自动跑一遍，状态栏补「已补上时长信息」。
**回归**：PC 与手机视口快速编码仍是 `MP4`（AAC 路径没动）；PC 录制仍 `可拖进度`、4.67s / 音频 4.63s / 可 seek。

### v50（10-31）：默认仍是 MP4 —— 不再用 isConfigSupported 否决 H.264
**用户反驳**：「默认导出是 mp4 呀，之前手机编码导出也是 mp4」。判断成立：上一版把「AAC 查询不支持」当成事实，直接跳过所有 avc1 候选 → 整条掉成 WebM；后续又用 PCM 兜底，结果连 MP4 都没了。
1. **能力查询不可信**：`AudioEncoder.isConfigSupported({codec:'mp4a.40.2'})` 在部分安卓内核会误报（说没有、真编却有）。现在 `pickExportFormat` 对 mp4 **只记预判、不据此否决**：`audioOk` 直接给 true，真伪交给 `encodeAudioTrack` 里那次真实编码。
2. **真失败才退 PCM**：AAC 编码抛错或没出帧 → 同一份样本改写成未压缩 PCM，`usedPCM=true`；`encodeMovie` 用 `pcmOut = audioRes.usedPCM` 决定品牌（MOV）与扩展名。`fmt.audioPCM` 降级为纯提示。

4. **aacWorks()**：真编 4096 帧来判断 AAC 是否可用（1024 帧会 `flush` 报「Flushing error」，是探测方法问题，不是设备问题）。转换器与 `willUsePCM` 都用它，替代 isConfigSupported。
**实测**：① 把 isConfigSupported 打桩为「不支持 AAC」→ 仍导出 `MP4 1280×720 · 0.9 MB`，boxes: mp4a=true / sowt=false，音频解码 2.99s；② 让 configure 真抛错 → `MOV · 1.4 MB`，sowt=true、音频 3.00s；③ PC 录制仍 `MP4 / 可拖进度 / 4.67s`；④ 手机视口与 WebM-only 设备均回到 `已导出 MP4`、`已自动转成 MP4`。

### v51（10-31）：录制转 MOV 后音画不同步（真凶：转换时按 30fps 等距写帧）+ AAC 换码率重试
**用户反馈**：手机录制转出的 MOV 能播，但 4:06 的片子画面 2:50 就播完、声音走到 4:08；手机快速编码仍是 MOV。

### v52（10-31）：手机无 AAC 的实证 + 音轨起点对齐 + HE-AAC 兜底
**证据（用户截图）**：`Failed to execute 'configure' on 'AudioEncoder': Unsupported codec type` —— 这台手机的浏览器**根本没注册 AAC 编码器**，不是码率/采样率问题。MP4 容器只认 AAC，所以带声音的 MP4 在这台机器上物理不可行；「之前能导 MP4」只能是当时那个内核还带 AAC（后来被裁掉），或那次其实在电脑上导的。
1. **音轨起点对齐**：`convert()` 里音频原来从 0 连续写，抹掉了 WebM 里音/视频第一条块的时间戳差（几十毫秒）。改成以画面第一帧为 0：音频晚 `headPad` 就补静音，早 `-headPad` 就裁掉；中途丢包（`d.timestamp` 跳变 >3ms）也补静音。
2. **HE-AAC 兜底**：AAC 候选从「只换码率」扩成「换编码器 + 码率」：`mp4a.40.2 @192k/128k/96k → mp4a.40.5 @64k`。部分内核只登记 HE-AAC。
3. **每包采样数按时间戳算**：LC=1024、HE=2048，写死 1024 会让 HE 变半速；`MP4.build` 里 `aPer`（音频自带时长）时跳过按 1024 的尾部截断。
**实测**：快速编码 3s（5s 音频）→ 视频轨 3.00s / 音频轨 3.008s / 解码 3.01s；20fps 的 7.9s 录制转换 → 视频 7.93s / 音频 7.94s（对齐）。
**遗留**：手机录制只有 ~20fps，画面本身偏卡；开头约 0.4–0.5s 静止（热身）仍保留，所以成片比音频长一点点。

### v55（10-31）：收尾优化第一批 —— M1 全链路闸门 + M2 预算模型
**用户要求**：优先设计机制；不得破坏现有功能、不引入新 bug；覆盖两种导出的崩溃、大文件、多格式、长时间、导出质量。
**需求检查结论**：多格式已较好（WMA/APE/AIFF 导入即报、HEIC 拒绝、封面 >2400px 自动降采样、>800MB 音频有提醒）；真正的空白是「长音频导入」「补时长无闸门」「预算低估分片内存」。
1. **M1-a 音频导入硬闸门**：新增 `probeAudioSeconds(file)`（临时 audio 元素量时长，不动 state），估算 `PCM = 时长 × 0.366 MB/s`（48k 立体声 float32）。> **1800MB**（≈80 分钟）直接拒收，不进入解码。阈值取 1800 而非 1200，是为了不削掉原有「60 分钟音频」能力。实测：90 分钟/82MB 的 WAV 在 93ms 内被拦，`audioBuf` 保持 null，状态栏给出「约 1976 MB，超过上限 1800」。
2. **M1-b 补时长闸门**：`fixWebm` 要整片读进内存，> 400MB 跳过并说明「太大没补时长索引」（之前完全没有闸门，2GB 必崩）。
3. **M2 预算模型重写**：`estimateMemMB` 拆成 `memBreakdown()`——音频 PCM 全额 + 视频分片按 **50%**（原 15%，对内存分片太乐观）+ 素材画布（55MB × 面积比）。`suggestMaxSeconds` 同步改用新口径；超限文案直接列三项与总额，用户能看出该改哪个数。

### v58（10-31）：首屏 / 交互 / 内存专项优化（不改导出算法）
**测量环境**：Edge 156 headless + file://，CDP `Performance`/`Profiler` 采样；新旧版本交替采样抵消机器负载漂移。
**首屏**
| 指标 | 改前 | 改后 |
|---|---|---|
| HTML 解析（responseEnd→domInteractive） | 586–619ms | **32–51ms** |
| 启动 JS（interactive→FCP） | 560–590ms | **207–337ms** |
| FCP | 2588–2724ms | **1828–2224ms** |
| `<style>` 体积 / 规则数 | 6.40MB / 171 | **0.02MB** / 166 |
1. **字体的 6.4MB base64 从 `<style>` 挪到 `#fontStore`（`<script type="text/plain">`）**：CSS 解析器要对每个 base64 URL token 做完整词法分析+字符串驻留，HTML 解析器只做一次纯文本扫描（找 `</script>`）。这是 parse 从 600ms 降到 40ms 的唯一原因。
2. **FontFace 懒加载**：`ensureFontLoaded` 改成从 `#fontStore` 取 base64 → `new FontFace(...)` → `document.fonts.add`，注册完 `node.textContent=''` 释放常驻。默认字体是 sans，所以首屏一个字体都不解。
3. **字体探测挪出首屏**：`buildFontOptions({quick:true})` 只列「内置 5 + 通用 3 族」，`requestIdleCallback(1200 超时)` 再补本机已装字体（探测要对每个字族做 3 次 canvas 测量，实测 133ms）。
**交互**（同一组用例 A/B）
| 用例 | 改前 | 改后 |
|---|---|---|
| 连发 60 次字号滑块 input（同步阻塞） | **1506.5ms** | **0.7ms** |
| 连打 20 个歌词字符 | 10.1ms | 5.4ms |
4. `refreshPreview(rebuild)`：滑块/颜色/歌词打字全部合并到下一帧，一帧只 `buildLayout+renderAt` 一次。**注意只有「预览刷新」走这条路**，seek/导出仍同步。
5. 切页签的重绘移到 `requestAnimationFrame`，滑动动画先起步。
6. **去掉 header / .mtab 的 `backdrop-filter:blur(14px)`**：这两个是 sticky/fixed，滚动时每帧要对整宽做一次高斯模糊。改为 `rgba(...,.97)` 实色（视觉几乎无差，见截图）。
**导出（实测已到硬件上限，只落了一处）**
7. `renderAt` 有 `assets.bg` 时不再先铺底色（buildBg 第一笔就是整屏不透明填充）→ 每帧省一次 1920×1080 全屏 fill。1080p 20s：10.9s→10.7s。
**四个被实测否决的方向（别再试）**：① 让出策略 all/2帧/time(12ms)/不让 —— 5.28/5.30/5.29/5.33 全等；② `latencyMode:'realtime'` —— 3.28 vs 3.32（噪声，且降画质）；③ `bitrateMode:'constant'` —— 同样无提速；④ **双 VideoEncoder 并行** —— 2.51/2.48 vs 2.61/2.44，无提速（核显只有一个编码引擎，会话排队）。
**CPU/内存**
8. 空闲 3s 主线程 TaskDuration = **0ms**（本来就干净）；导出后 JS 堆 3.7MB → GC 后 1.1MB（无泄漏）。
9. **导出内存护栏**：每 32 帧查 `performance.memory`，超 1200MB（手机）/2600MB（PC）主动停并给原因 —— 被系统杀是一无所有，主动停至少能说明。
**回归**：PC 带音频 MP4 2.4MB；PC 录制 4.75s/音频 4.59s/可拖；手机视口 0.4MB/1.8×；WebM-only 设备自动转 MP4；无 AAC → MOV+PCM 音频 3.00s；预算闸门/下拉互斥/字体 15 组两两不同 全部通过。

### v59（10-31）：并发/泄漏/长稳加固 + 压测与扫描
**一、机制（4 个，全部新增，导出算法未动）**
1. **任务号** `beginJob()/jobOK()`：每次点击导出/开始录制领一个号；快速编码的下载与状态写入、录制重封装的收尾，都先校验号。作废任务的回调**既不下载也不改状态、也不碰 busy**（否则会出现「文件下好了、状态是上一次的」或把新任务的 busy 关掉）。
2. **导入序号**：`loadImageFile`/`loadAudioFile` 各一个自增序号，异步结果回来先比对，晚到的结果直接丢弃（音频有 3 个 await 点：量时长后、metadata 后、decode 后）。
3. **日志环**：200 条内存环形缓冲（时间/级别/标签/内容），`logDump()` 一键导文本；默认**零 console 输出**（导出时打日志是纯 I/O 负担），`?debug=1` 才同时打 console。记录启动能力、素材载入、录制起止、导出成功/失败/取消、内存自愈。
4. **可见性 + 自愈**：IntersectionObserver 让预览离屏时停止重绘（手机翻到「样式」页不再空跑 rAF）；切回页面时若 JS 堆 > 700MB，清字形缓存 + 释放大音频 PCM。

### v60（10-31）：性能验收专项（首屏再降 350ms + 热路径 + 逐条核对）
**一、这轮真正改的 4 处**
1. **首帧渲染改到「第一帧之后」**（最大收益）：`applyLayout + renderAt(0)` 从同步启动块移出，用**两级 rAF**（单级无效——rAF 回调在绘制之前执行）。`renderAt` 开头加 `if(!assets.bg) return;` 防止画出半成品。画布容器本身有 `#07131d` 底色 + `aspect-ratio:16/9` 占位，所以既不白闪也不抖动（CLS 实测仍为 0）。
